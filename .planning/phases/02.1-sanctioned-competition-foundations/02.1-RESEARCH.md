## Summary

Phase 2.1 closes the operational gaps that prevented fartOLa from running as primary system at the 4-klubbs event on 2026-05-20. The target is Gundes Sommarsprint in June 2026. The phase is primarily additive — new algorithms, new schema columns, new routes — on top of a well-understood existing stack.

The three most technically novel areas are: (1) the SOFT draw algorithm, which is a well-defined permutation/interleave procedure documented in MeOS source and re-implementable cleanly in TypeScript; (2) the kvar-i-skogen backup readout, which uses SPORTident protocol commands already defined in `packages/sportident/src/constants.ts` but never yet called in a backup-read context; and (3) the liveresultat push protocol, which is an HTTP POST with form fields (`competition`, `pwd`) and an XML body — the protocol itself is simple but the format decision (MOP XML 2.0 vs IOF XML 3.0) needs a conscious choice.

Responses are `<ImportStartListResult>` and `<ImportResultListResult>` XML. This is the same API key already configured in the project from Phase 2.0.

The carry-over plans (02-08, 02-09, 02-10) are already fully specified and ready to execute without further research.

**Primary recommendation:** Execute Phase 2.1 as a sequence of focused plans: schema + start list core → kvar-i-skogen → liveresultat push → Eventor push → gap wins (MAX auto-compute, voided legs, replacement controls, Cancelled status) → carry-overs (02-08, 02-09, 02-10) → test harness.

### Pattern 1: SOFT Draw Algorithm (D-04)

**What:** Club-blocking draw. Group runners by club → distribute club-groups into N bins (N = max club size) → recursive permutation within sub-groups → interleave by level.

**Verified against:** `/home/jonas/src/meos/code/oEventDraw.cpp` lines 130-209 (GPL — re-authored, not ported).

**TypeScript re-authoring:**
```typescript
// Source: oEventDraw.cpp:130-209 (GPL, re-authored)
// Not a port — the algorithm is described publicly in orienteering draw
// literature. Implementation re-authored in TypeScript.
export function drawSOFT(runners: Runner[]): Runner[] {
  if (runners.length === 0) return [];

  // 1. Group by club
  const byClub = new Map<string, Runner[]>();
  for (const r of runners) {
    const clubKey = r.club ?? '__none__';
    if (!byClub.has(clubKey)) byClub.set(clubKey, []);
    byClub.get(clubKey)!.push(r);
  }

  // 2. Find largest club → that becomes group 0
  let largest: Runner[] = [];
  let largestKey = '';
  for (const [k, v] of byClub) {
    if (v.length > largest.length) { largest = v; largestKey = k; }
  }
  byClub.delete(largestKey);

  const largeSize = largest.length;
  const nBins = Math.ceil(runners.length / largeSize);
  const groups: Runner[][] = [shuffleArray(largest)];
  for (let i = 1; i < nBins; i++) groups.push([]);

  // 3. Distribute remaining clubs into smallest available group
  while (byClub.size > 0) {
    let smallestIdx = 1;
    for (let i = 2; i < groups.length; i++) {
      if (groups[i].length < groups[smallestIdx].length) smallestIdx = i;
    }
    let [nextKey, nextClub] = [...byClub.entries()].reduce(
      (max, entry) => entry[1].length > max[1].length ? entry : max
    );
    byClub.delete(nextKey);
    groups[smallestIdx].push(...nextClub);
  }

  // 4. Recursively apply to groups 1..N-1 (pad to same size with nulls for blanks)
  const maxSize = Math.max(...groups.map(g => g.length));
  for (let i = 1; i < groups.length; i++) {
    groups[i] = drawSOFT(groups[i]); // recursive
  }

  // 5. Permute group order, then interleave by level
  const permutedGroups = shuffleArray(groups);
  const result: Runner[] = [];
  for (let level = 0; level < maxSize; level++) {
    for (const g of permutedGroups) {
      if (level < g.length) result.push(g[level]);
    }
  }
  return result;
}
```

### Pattern 2: Kvar-i-skogen Backup Readout

**What:** Read BSF8 check-unit backup memory via SPORTident extended protocol. Two-step: GET_SYS_VAL (0x83) for memory pointer + overflow flag, then loop GET_BACKUP (0x81) in 128-byte chunks.

**Existing constants** (`packages/sportident/src/constants.ts`):
```typescript
cmd: {
  GET_BACKUP: 0x81,   // already defined
  GET_SYS_VAL: 0x83, // already defined
  // ...
}
proto.REC_LEN = 8;   // 8 bytes per record in extended protocol
proto.BC_CN = 3;     // card number offset in backup record
proto.BC_TIME = 8;   // time offset in backup record (not present in constants yet — see pitfall)
```

**New function** `packages/sportident/src/SiStation/readBackup.ts`:
```typescript
// Source: pcprog5-v11-2018-10-15/pcprog5.pdf §3 (do not commit)
// and BSx7_8_readbackup.txt from the same reference set.
// Re-authored against the pcprog5 spec, not ported.
export async function readBackupMemory(
  station: SiMainStation
): Promise<Array<{ cardNumber: number; punchTime: HalfDayClock | null }>> {
  // Step 1: GET_SYS_VAL → memory pointer + overflow flag
  const sysVal = await station.sendCommand(proto.cmd.GET_SYS_VAL, ...);
  const memPointer = parseMemPointer(sysVal);
  const hasOverflow = parseOverflowFlag(sysVal);

  // Step 2: Loop GET_BACKUP in 128-byte blocks
  const records: BackupRecord[] = [];
  let offset = 0;
  while (offset < memPointer || (hasOverflow && offset < MAX_MEM)) {
    const block = await station.sendCommand(
      proto.cmd.GET_BACKUP, offset >> 8, offset & 0xFF
    );
    records.push(...parseBackupBlock(block));
    offset += BLOCK_SIZE;
  }
  return records;
}
```

**Edge route** `POST /api/checkunit/snapshot`:
- Opens serial port for the plugged-in check unit (operator specifies port or uses existing bridge connection)
- Calls `readBackupMemory`
- Returns `{ cardNumbers: number[], overflow: boolean, readCount: number }`
- Caller diffs against `finish_set` in the projection

### Pattern 3: Liveresultat Push Protocol

**What:** HTTP POST to operator-configured URL with form fields and XML body.

**Source:** MeOS `onlineresults.cpp:504-598` (GPL, re-authored) + project memory `reference_liveresultat.md` [VERIFIED: MeOS source].

**Protocol details** [VERIFIED: MeOS source]:
- **URL:** Operator-configured (e.g., `https://liveresultat.orientering.se/upload.php` — exact URL registered on liveresultat site)
- **Method:** HTTP POST
- **Form fields:** `competition=<id>` + `pwd=<password>` (both registered by operator on liveresultat site)
- **Body:** XML file (MOP XML 2.0 recommended — liveresultat is built to consume it)
- **Compression:** Optional ZIP (Content-Type: `application/zip` when zipped, `text/plain` when not)
- **Chunked upload:** MeOS splits large payloads at 64-record chunks; for Phase 2.1 a single full-snapshot push is sufficient
- **Response:** `<MOPStatus status="OK"/>` or `BADCMP|BADPWD|NOZIP|ERROR`

**Format decision (Claude's Discretion):** Use **MOP XML 2.0** format (not IOF XML 3.0).

Rationale: liveresultat.orientering.se is specifically designed to consume MOP XML 2.0 — it is the native format. The fartOLa edge server already receives MOP XML from MeOS via the MOP receiver route; re-using those same structures for output is natural. MeOS uses IOF XML 3.0 only as a fallback ("general file format that always works" per LiveResults docs).

For Phase 2.1, fartOLa will emit a simplified MOP XML 2.0 `<MOPComplete>` snapshot with `<competition>`, `<cls>`, `<org>`, and `<cmp>` elements. Start times in tenths of a second (MOP convention).

**Failure isolation** (D-10): Push runs on a separate async queue. `local results → SQLite` happens synchronously; push enqueues and retries in the background. A failed push logs an error but never propagates to the operator route handler.

### Anti-Patterns to Avoid

- **Blocking the route handler on liveresultat push.** Push to a background queue; return 200 to the operator immediately.
- **Parsing the BSF8 backup block without the pcprog5 spec.** The memory layout is not trivially deducible from the raw bytes. Use `proto.BC_CN = 3` and `proto.BC_TIME = 8` offsets (extended protocol backup mode).
- **Calling `drawSOFT` synchronously in the route for large classes.** For 200 runners it is fast (<1ms), but if ever run on a relay with 1000 runners, it could stall. Run it synchronously for Phase 2.1 (no async needed), but document the limit.
- **Using MeOS's `drawSOFTMethod` implementation as-is.** It operates on `pRunner*` C++ pointers; the TypeScript re-authoring is conceptually identical but must be cleanly re-authored against the algorithm description, not translated from C++ pointer semantics.
- **Setting `--bind-host 0.0.0.0` without admin code protection.** Plan 02-08 (admin codes) MUST be deployed before advertising LAN access. Admin codes gate all write routes for non-localhost requests.

## Common Pitfalls

### Pitfall 1: BC_TIME offset in BSF8 backup records

**What goes wrong:** The backup memory record layout differs between basic protocol and extended protocol. `proto.BC_TIME = 8` is the **control-mode** offset, not the check-punching offset. BSF8 in mode 0x02 (Check) stores records differently from BSF8 in mode 0x03 (Control).

**Why it happens:** The pcprog5 §3 table shows multiple record formats depending on station mode. The `BSx7_8_readbackup.txt` reference clarifies which applies to check-unit mode.

**How to avoid:** Bench-test against a real BSF8 with known punch records. Commit a fixture pair (raw bytes + expected card numbers) as a regression test before shipping. The `.reference/` dir is gitignored — test with a local device first.

**Warning signs:** Card numbers parse as 0 or as impossible values (>9999999).

### Pitfall 2: SOFT algorithm with all runners from same club

**What goes wrong:** If all runners in a class belong to one club, `clubRunner` has only one entry. The algorithm trivially returns a random permutation. This is correct behavior, but must be tested explicitly — MeOS's `largeSize` calculation would set `ngroups=1`, so the interleave loop does nothing.

**How to avoid:** Unit test: 10 runners from same club → result is 10 runners in random order (no crash, no duplicates).

### Pitfall 3: Liveresultat `competition` field is an integer, not the event name

**What goes wrong:** The competition ID on liveresultat.orientering.se is a numeric ID assigned when the operator registers the event. It is NOT the Eventor event ID and NOT the fartOLa competition UUID.

**How to avoid:** Store liveresultat `competition_id` and `password` on the competition row (or in settings). The operator must register the event on liveresultat.orientering.se first and obtain the ID. Document this in the operator runbook.

**Schema addition needed:** `competitions.liveresultat_id TEXT NULL` + `competitions.liveresultat_pwd TEXT NULL` (password stored encrypted similar to Eventor API key).

### Pitfall 4: Eventor import/startlist rejects non-UTC timestamps

**What goes wrong:** Eventor's startlist import is sensitive to timestamp format. MeOS has a `UseEventorUTC` property that controls whether exported times are in UTC or local time. Without UTC, Eventor may reject the upload or misparse times.

**How to avoid:** Always emit UTC (`Z` suffix) in IOF XML 3.0 `<StartTime>` elements for Eventor push. The existing `iofExport.ts` produces `event_time_ms` from the SQLite event log which is always epoch ms (UTC by definition).

### Pitfall 5: MOP XML time units are tenths, not milliseconds

**What goes wrong:** fartOLa stores all times in milliseconds internally. MOP XML 2.0 uses **tenths of a second** for start times and running times. Off-by-10 errors are silent (results look plausible but are 10x wrong).

**How to avoid:** Conversion: `mop_tenths = Math.round(ms / 100)`. Start time in MOP is tenths after competition zerotime (race_started_at_ms), not epoch. Test with a known card read and verify the MOP output matches the expected split time.

### Pitfall 6: Multi-serial — both readers report the same card

**What goes wrong:** If two readers are configured and the same card is inserted in both (unlikely but possible), two `card_read` events land. The reducer is idempotent on duplicate card reads (later one wins), but the walk-up modal would flash twice.

**How to avoid:** The existing card dedup logic in `cardQueue.svelte.ts` (FIFO + dedupe) handles this. Verify the dedupe window covers the cross-reader case.

### Pitfall 7: drizzle-kit migration numbering collisions with carry-over plans

**What goes wrong:** Plans 02-09 and 02-10 include specific migration filenames (0003 and 0004). But the project is already at migration 0006 (confirmed from `_journal.json`). If carry-over plan migrations use old numbering, drizzle-kit will reject or silently skip them.

**How to avoid:** The carry-over plans (02-09, 02-10) reference filenames like `0003_eventor_si_card_dedupe.sql` but migration 0003 already exists (`0003_sharp_greymalkin.sql`). The planner MUST renumber these to the next available slots (0007, 0008, etc.) and update the Drizzle journal accordingly. This is not a code change — it's a plan adjustment.

**Current migration state (from `_journal.json`):**

```
0000_initial → 0001_append_only_triggers → 0002_phase2 → 0003_sharp_greymalkin
→ 0004_eventor_fts → 0005_busy_iron_monger → 0006_eventor_fts_update_triggers
```
**Next available:** `0007_...`

### Pitfall 8: IOF XML 3.0 StartList uses `<ClassStart>` not `<ClassResult>`

**What goes wrong:** The existing `iofExport.ts` builds `ResultList` with `<ClassResult>` and `<PersonResult>`. StartList uses `<ClassStart>` and `<PersonStart>` with `<Start>` children. The element names are different — naively copy-pasting the builder produces invalid XML.

**How to avoid:** Reference the bundled `IOF.xsd` (already at `apps/edge/src/xml/IOF.xsd`, 173 KB) for the StartList element structure. Run `xmllint-wasm` validation on any StartList output before shipping. The `validate.ts` infrastructure is already in place.

### Eventor push function (results)

```typescript
// Source: MeOS TabCompetition.cpp:1221-1314 (GPL, re-authored)
// Endpoint confirmed: POST {eventorBase}import/resultlist
export async function pushResultListToEventor(opts: {
  apiKey: string;
  eventorBase: string;
  xmlBody: string;          // IOF XML 3.0 ResultList string
  fetchImpl?: typeof fetch;
}): Promise<{ resultListUrl: string }> {
  const url = `${opts.eventorBase}import/resultlist`;
  const zipped = await zipString(opts.xmlBody);  // zlib deflate → zip
  const res = await (opts.fetchImpl ?? fetch)(url, {
    method: 'POST',
    headers: {
      'ApiKey': opts.apiKey,
      'Content-Type': 'application/zip',
    },
    body: zipped,
  });
  if (!res.ok) throw new Error(`Eventor import failed: ${res.status}`);
  const xml = await res.text();
  // Parse <ImportResultListResult><ResultListUrl>...</ResultListUrl></ImportResultListResult>
  const match = xml.match(/<ResultListUrl>([^<]+)<\/ResultListUrl>/);
  return { resultListUrl: match?.[1] ?? '' };
}
```

### Liveresultat push function

```typescript
// Source: MeOS onlineresults.cpp:504-598 (GPL, re-authored)
// Protocol confirmed: project memory reference_liveresultat.md
export async function pushToLiveresultat(opts: {
  url: string;            // operator-configured upload URL
  competitionId: string;  // numeric ID from liveresultat site
  password: string;
  mopXml: string;         // MOP XML 2.0 <MOPComplete> body
  fetchImpl?: typeof fetch;
}): Promise<void> {
  const formData = new FormData();
  formData.append('competition', opts.competitionId);
  formData.append('pwd', opts.password);
  // MOP XML as text/plain (no zip for Phase 2.1 initial implementation)
  formData.append('', new Blob([opts.mopXml], { type: 'text/plain' }));
  const res = await (opts.fetchImpl ?? fetch)(opts.url, {
    method: 'POST',
    body: formData,
  });
  const xml = await res.text();
  if (!xml.includes('status="OK"')) {
    throw new Error(`Liveresultat push rejected: ${xml}`);
  }
}
```

**Note:** The exact Content-Type and body encoding MeOS uses is `postFile()` which is a WinInet multipart upload. The `fetch`+`FormData` equivalent is the standard Node 22 approach. Verify against a real liveresultat sandbox before production use.
