# Cross-AI Plan Review — Phase 02.1

## GPT-5.5 Review (xhigh)

### Summary

The Phase 2.1 plan set is unusually thorough and generally well-aligned with the Gundes Sommarsprint goal: start-list drawing, Eventor push, liveresultat push, kvar-i-skogen, multi-serial, admin access, and MeOS interop are all covered. The main risks are not architectural direction but execution correctness: migration sequencing across many PRs, inconsistent time semantics, several protocol assumptions that need real-world verification, and a few plans whose stated success criteria are not fully implemented by their task lists. Overall risk is **MEDIUM-HIGH** until the dependency graph and protocol validation gaps are tightened.

### Strengths

- The plans are grounded in specific project context, existing code entry points, and prior decisions rather than generic implementation advice.
- The phase scope is practical: Yjs, spectator pages, peer sync, and other larger features are correctly deferred.
- The plans emphasize tests, route-level validation, threat modeling, and acceptance criteria.
- External integrations are separated into focused modules with `fetchImpl` seams and mockable tests.
- The event-day operational goals are visible throughout: two operators, backup via MeOS, start lists, safety check, and non-blocking live-result push.
- Carry-over work is mostly renumbered and folded into the phase instead of being left as vague backlog items.

### Concerns

- **HIGH — Migration sequencing conflicts.** Plans 01, 10, 11, and 12 create migrations `0007` through `0010`, but the declared waves/dependencies still allow conflicting parallel work. Plan 10 has `depends_on: []` while assuming `0007` exists; Plan 12 can run in the same wave as Plan 11 while assuming `0009` precedes `0010`.
- **HIGH — Time semantics are inconsistent.** `first_start_ms` / `start_time_ms` are described alternately as epoch milliseconds, competition-relative milliseconds, after-midnight tenths, and race-zero-relative values. This affects lottning, IOF StartList, Eventor push, MOP XML, UI display, and thermal printing.
- **HIGH — Some protocol-critical pieces rely on assumptions.** BSF8 backup parsing, liveresultat multipart encoding, MOP status/time fields, and Eventor ZIP format all need explicit sandbox/hardware verification before event-day use.
- **MEDIUM — Several plans state acceptance criteria that are not matched by files/tasks.** Examples: Plan 03 thermal printing without print files, Plan 05 class max-time editing without backend class PATCH support, Plan 04 position-aware routing without frontend queue updates, and Plan 01 Cancelled IOF mapping without `iofExport.ts` changes.
- **MEDIUM — Security sequencing around LAN access is fragile.** Multi-serial/LAN work appears before admin codes, and write-route protection needs an explicit route inventory to avoid accidental gaps or blocking required public routes.

### Suggestions

- Add an explicit dependency chain for migration-bearing plans: **02.1-01 → 02.1-10 → 02.1-11 → 02.1-12**. Do not run those PRs in parallel unless each is rebased after the previous migration lands.
- Define one canonical time model before implementation. Recommended: store `start_time_ms` as absolute UTC epoch milliseconds in the DB, derive display/local HH:MM from event timezone, derive MOP tenths through a shared helper, and test all conversions.
- Add a short "protocol verification wave" before production hardening: BSF8 real-device readout, Eventor ZIP upload against a test event, liveresultat sandbox push, and a known SOFT draw comparison against MeOS.
- Add missing ownership to plans: frontend reader-position routing, class settings PATCH, timing-display persistence, thermal-print template files, external integration config/status UI, and Eventor/liveresultat operator runbook steps.
- Treat external push integrations as observable systems: store last push status/error/time, expose it in UI, and provide a manual retry button.
- For safety-critical kvar-i-skogen, distinguish "physically read out / known safe" from computed result status. Do not rely only on OK/MP/DNF/DQ/MAX status as the finished set.

## Gemini 3.5 Review (flash)

### Summary

The overall structure of the delivery is exceptionally clean: the database schema migrations have been correctly consolidated into Wave 1 (renumbered to slots `0007`-`0010` to respect the existing migration journal), the core algorithms are re-authored to avoid GPL porting issues, and the interop/safety gaps are cleanly addressed.

### Plan-by-Plan Review

#### 02.1-01 — Wave 1: Schema Migration 0007 & Reducer Extensions
* **Summary**: Lays down the database columns (`classes`, `competitors`, `competitions`, and the `course_replacements` table) and reducer extensions (MAX auto-compute, voided legs, replacement controls) that underpin all downstream plans.
* **Strengths**:
  * Consolidating all Phase 2.1 schema adjustments into Wave 1 is a superb scheduling decision.
  * The MAX status auto-computation is beautifully integrated into the reducer pipeline right after `dnfMp.detectStatus` and respects manual overrides.
  * Voided legs and replacement controls are cleanly modeled as event-sourced updates in `reduce.ts`.
* **Concerns**:
  * **MEDIUM SEVERITY (Infinite Loops in Reducer)**: If there are nested or cyclic entries in the `course_replacements` table (e.g., control 31 maps to 32, and 32 maps back to 31, or a long chain like 31 -> 32 -> 33 -> 34), a recursive replacement resolution in `reduce.ts` could trigger call stack exhaustion or infinite loops.
  * **LOW SEVERITY (Migration Locking)**: Adding nullable columns to existing tables in SQLite is fast, but creating new tables and indexes must be strictly wrapped in transactional DDL to avoid partial migration states during field deployments.
* **Suggestions**:
  * Implement an explicit recursion limit (e.g., maximum depth of 3) or cycle detection when resolving alternative codes via the `course_replacements` map in the reducer.
  * Ensure the generated `0007_phase2_1_schema.sql` wraps all ALTER and CREATE operations in a `BEGIN TRANSACTION;` and `COMMIT;` block.

#### 02.1-02 — Wave 2: Start List Draw Algorithms & Lottning Route
* **Summary**: Implements the three draw modes (SOFT club-blocking, Random, Simultaneous/mass-start) and the lottning API route that writes start times to competitor rows.
* **Strengths**:
  * Re-authoring the SOFT club-blocking draw algorithm in pure TypeScript against the mathematical concept (interleaving club groups evenly) instead of porting C++ pointers from MeOS avoids GPL contamination while maintaining logic equivalence.
  * Using `crypto.randomInt` ensures unbiased shuffling over insecure pseudorandom generators (`Math.random`).
  * Elegant vacant slot distribution algorithm that spreads empty start times evenly.
* **Concerns**:
  * **MEDIUM SEVERITY (Overwriting Manual Adjustments)**: Clicking "re-lotta" on a class wipes prior `start_time_ms` for that class. If an operator has manually adjusted specific runners' start times (via the "andra starttid" action), a full class "re-lotta" will silently overwrite these edits.
  * **LOW SEVERITY (Simultaneous Vacant Slots)**: For mass starts (`Simultaneous`), the spacing interval is ignored, but it is unclear if `vacantSlots` are assigned start times or omitted.
* **Suggestions**:
  * Add a `is_manually_drawn` or similar flag to competitor start times, or prompt the operator with a warning modal before "re-lotta" if any runner in that class has manual start-time adjustments.
  * Document how the Simultaneous draw handles vacant slot values (they should be ignored or explicitly pruned).

#### 02.1-03 — Wave 2: IOF XML 3.0 StartList Export & Import
* **Summary**: Wires up compliant IOF XML 3.0 export and import routines, including XSD validation and thermal print layouts.
* **Strengths**:
  * Running `validateXml` with the official `IOF.xsd` schema inside `iofExport.ts` before returning results guarantees data compliance.
  * Timezone-safe UTC ISO string parsing and output prevent Eventor timing offset issues.
  * High-value reuse of existing thermal printer components for localized start list prints.
* **Concerns**:
  * **MEDIUM SEVERITY (Fuzzy Match Ambiguity)**: Importing a StartList and fuzzy-matching on competitor names/classes can lead to misallocated start times (e.g., "Anna Nilsson" matching "Anna-Karin Nilsson" or family names sharing similar substrings).
  * **LOW SEVERITY (Import Duplicates)**: If a runner has multiple records or registration errors, fuzzy matching might silently bind the start time to the wrong person.
* **Suggestions**:
  * During XML StartList import, returning a structured list of "exact matches" (via Eventor Person ID or SI card) and presenting a confirmation screen for any "fuzzy/ambiguous matches" lets the operator manually audit and confirm bindings.

#### 02.1-04 — Wave 2: Multi-Serial SI Readers
* **Summary**: Extends the edge server to support multiple concurrently active serial ports using a repeatable `--serial` CLI flag and position-aware WebSocket broadcasts.
* **Strengths**:
  * Position tagging (`left`/`right`) perfectly aligns with the two-operator registration desk workflow, routing walk-up modals to the correct client window.
  * Keeps excellent backward compatibility for single `--serial-path` setups.
* **Concerns**:
  * **HIGH SEVERITY (Serial Port Reconnection & Path Drift)**: On Linux/Debian, unplugging and re-plugging USB-to-serial adapters can cause device paths to change (e.g., `/dev/ttyUSB0` shifts to `/dev/ttyUSB1`). If the `--serial` arguments are hardcoded to paths, the bridge lifecycles will try to bind to locked or non-existent devices.
  * **MEDIUM SEVERITY (Modals Confused)**: If client browsers on the same LAN don't configure their workstation roles, both browsers might open the walk-up modal for a "left" beep, causing operator confusion.
* **Suggestions**:
  * Add a mechanism in the browser client UI (e.g., local storage setting) to choose the workstation's position identifier ("left" or "right"), so the frontend knows whether to suppress or display position-tagged WebSocket card reads.
  * Suggest running a system udev rule or querying serial numbers (by serialport autodiscovery) to map devices robustly rather than depending on raw `/dev/ttyUSB*` order.

#### 02.1-05 — Wave 3: LottningView UI & Start-Time Column
* **Summary**: Implements Svelte 5 operator interfaces for drawing start lists and displaying start times on Registration and Readout panels, alongside tenths-of-a-second timing options.
* **Strengths**:
  * Leverages Svelte 5 runes (`$state`, `$derived`) for highly reactive form states.
  * Clean integration of timing settings that format displays to tenths of a second while maintaining database millisecond integrity.
* **Concerns**:
  * **MEDIUM SEVERITY (Tenths Rounding Drifts)**: If split times are computed by subtracting rounded tenths-of-a-second timestamps rather than doing ms-subtraction first and *then* rounding, arithmetic drifts can occur where splits do not sum to the total elapsed time.
* **Suggestions**:
  * Always perform all arithmetic operations (elapses, splits) in raw millisecond precision on the client and edge server. Only round to tenths at the final rendering layer in Svelte components.

#### 02.1-06 — Wave 2: Kvar-i-skogen (Check-Unit Readout)
* **Summary**: Implements BSF8 check-unit backup memory extraction via SPORTident binary protocols to identify which runners have started but not yet finished.
* **Strengths**:
  * High-value, critical safety mechanism that allows operators to read check cards directly in the forest.
  * Direct extraction of card numbers and comparison against projection finish sets provides a robust safety ledger.
* **Concerns**:
  * **HIGH SEVERITY (Stale Punch "Ghosts")**: Check stations (BSF8) are rarely cleared between training events. If memory has wrapped around or contains old check punches from last week's competition, reading backup memory from offset `0` will pull old cards, causing "ghost" runners to appear as missing in the forest.
  * **MEDIUM SEVERITY (Read Loop Infinite Loop)**: If the parsed GET_SYS_VAL memory pointer is corrupt or the station returns a malformed high pointer, the read loop could iterate indefinitely if not bounds-capped.
* **Suggestions**:
  * Filter out backup card reads whose timestamps are outside a reasonable event window (e.g., older than 12 hours or before the zero time of today's race).
  * Enforce a hard maximum iteration cap on the GET_BACKUP loop based on physical BSF8 memory bounds (e.g., `MAX_MEM / BLOCK_SIZE`) to completely eliminate infinite loop risks.

#### 02.1-07 — Wave 3: Liveresultat Push Integration
* **Summary**: Implements automated or operator-triggered push of live results to `liveresultat.orientering.se` in MOP XML 2.0 format via an isolated async retry queue.
* **Strengths**:
  * Direct HTTP POST utilizing Node 22 built-in `fetch` + `FormData` is incredibly lightweight and avoids bloated dependencies.
  * The async queue retry pattern (D-10) is beautifully decoupled, ensuring that slow network connections in the forest never block instant local result computation.
  * Logger redaction is properly handled for sensitive passwords.
* **Concerns**:
  * **HIGH SEVERITY (Rate Limiting & Queue Congestion)**: If `fartola` enqueues and pushes a full `MOPComplete` XML snapshot on *every single card read* (meaning every time a runner finishes), the outbound queue will experience severe backup during peak finish hours (e.g., 50 finishes per minute). The liveresultat server will likely block or throttle the edge IP.
  * **MEDIUM SEVERITY (Out-of-Order Uploads)**: If a push fails, retries, and a subsequent newer push finishes before the retried push succeeds, stale result data can overwrite fresher data on the server.
* **Suggestions**:
  * Implement a **throttled debouncer** on the queue: instead of uploading on every single punch, queue the job but execute it at most once every 10-15 seconds, consolidating all interim card reads into a single comprehensive snapshot update.
  * Ensure the queue discards older, pending push jobs for a competition when a newer snapshot job is enqueued.

#### 02.1-08 — Wave 3: Eventor Results + Startlist Push

* **Concerns**:

* **Suggestions**:

#### 02.1-09 — Wave 2: MeOS classid Fix

* **Strengths**:
  * Solves a highly specific and annoying bug in MeOS's `restserver.cpp:1372` without patching the MeOS binary itself.
  * Clean, automated recovery via fallback to `classid="0"`.
* **Concerns**:
  * **LOW SEVERITY (API Overhead)**: Polling `?get=class` on *every* MIP poll cycle is highly wasteful. Classes do not change during active competition reads.
* **Suggestions**:

* **Concerns**:
  * **HIGH SEVERITY (Localhost Header Spoofing Bypass)**: Bypassing auth check for `localhost` requests is common, but checking headers like `X-Forwarded-For` can allow remote LAN users to spoof their IP as `127.0.0.1` and bypass security entirely.

* **Suggestions**:
  * Ensure the localhost bypass strictly queries `request.socket.remoteAddress` and does **not** trust proxy forwarding headers unless explicit local reverse proxies are used.
  * Store the cookie signing secret in the local SQLite database or config file so edge server reboots do not invalidate volunteer helpers' active sessions.

### Phase-Level Risk Assessment

* **Overall Risk Level**: **MEDIUM**

#### Justification
Phase 2.1 is highly additive, clean, and addresses the absolute core functional gaps preventing `fartola` from running sanctioned events. The risk is classified as **MEDIUM** primarily due to:
1. **Physical/Hardware Interactions (Plan 06)**: Reading check-unit backup streams can expose stale historical punches, requiring rigorous time-filtering to avoid "ghost" starts.
2. **Network/Rate Limits (Plan 07)**: Pushing results per-finisher to Liveresultat can cause out-of-order state overwrites and outbound connection choke-points on slow forest LANs without proper debouncing/coalescing.

By adopting the suggested debouncing on Liveresultat uploads, enforcing timestamp window constraints on BSF8 check readouts, and securing the localhost IP bypass against header spoofing, this phase can be safely, securely, and successfully executed.
